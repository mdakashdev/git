আপনি যদি **Claude Code** ব্যবহার করেন, তাহলে আপনার সবচেয়ে গুরুত্বপূর্ণ সেটআপ সময়টি এখানেই সবচেয়ে বেশি কাজে লাগে।

**CLAUDE.md** হলো একটি Markdown ফাইল, যা Claude প্রতিটি নতুন সেশনের শুরুতে স্বয়ংক্রিয়ভাবে পড়ে। এতে এমন সব **প্রজেক্ট-নির্দিষ্ট নির্দেশনা** থাকে, যেগুলো না হলে আপনাকে বারবার প্রতিটি প্রম্পটে লিখতে হতো। যেমন—প্রজেক্টের কাঠামো, কোডিং কনভেনশন, ওয়ার্কফ্লো, স্টাইল ইত্যাদি।

## কেন আপনার একটি `CLAUDE.md` ফাইল প্রয়োজন

Claude প্রতিটি নতুন সেশন শুরু করে **কোনো পূর্ববর্তী স্মৃতি ছাড়াই**। আগের সেশনে কী হয়েছে, তা সে জানে না।

সে জানে না—

* আপনার কোড লেখার পছন্দের স্টাইল কী।
* আপনি কীভাবে টেস্ট চালান।
* আপনার টিম নির্দিষ্ট কোনো ব্রাঞ্চ নামকরণের নিয়ম অনুসরণ করে কিনা।
* অথবা আপনার অথেনটিকেশন মডিউলে কোনো বিশেষ ওয়ার্কঅ্যারাউন্ড (workaround) আছে কিনা।

ফলে আপনাকে একই বিষয় বারবার বুঝিয়ে বলতে হয়।

আরও খারাপ হলো, কখনও কখনও আপনি গুরুত্বপূর্ণ কোনো বিষয় উল্লেখ করতেই ভুলে যান। তখন Claude এমন কোড লিখে, যা আপনার টিমের নিয়ম বা কনভেনশন অনুসরণ করে না। পরে সেই কোড ঠিক করতে অতিরিক্ত সময় নষ্ট হয়।

**CLAUDE.md** এই সমস্যার সমাধান করে। Claude প্রতিবার নতুন সেশন শুরু করার আগে এই ফাইলটি স্বয়ংক্রিয়ভাবে পড়ে, ফলে আপনার নির্দেশনা, পছন্দ এবং কাজের নিয়ম প্রতিটি সেশনেই বজায় থাকে।

# কীভাবে আপনার `CLAUDE.md` ফাইল তৈরি করবেন

শুরু করার সবচেয়ে দ্রুত উপায় হলো **`/init`** কমান্ড ব্যবহার করা। 

আপনার প্রজেক্ট ডিরেক্টরিতে এই কমান্ড চালালে, Claude আপনার প্রজেক্টের কাঠামো এবং ব্যবহৃত টেক স্ট্যাক বিশ্লেষণ করে একটি প্রাথমিক (starter) **`CLAUDE.md`** ফাইল তৈরি করে দেয়।

অনেকে শুরু থেকেই নিজে হাতে পুরো ফাইল লেখার পরামর্শ দেন। তবে আমি **`/init`**-কে একটি ভিত্তি হিসেবে ব্যবহার করি এবং পরে যেগুলো দরকার নেই, সেগুলো মুছে দিই। কারণ, শূন্য থেকে সবকিছু লেখার চেয়ে অপ্রয়োজনীয় অংশ মুছে ফেলা অনেক সহজ।

Claude যে ফাইলটি তৈরি করে, তাতে প্রায়ই এমন কিছু বিষয় থাকে যেগুলো খুবই স্বাভাবিক বা স্পষ্ট, তাই আলাদাভাবে লেখার দরকার হয় না। আবার কিছু অংশ শুধুই অতিরিক্ত তথ্য (filler), যা আসলে তেমন কোনো মূল্য যোগ করে না।

কারণ হলো, **কনটেক্সট (Context) খুবই মূল্যবান।** আপনার `CLAUDE.md`-এর প্রতিটি লাইন Claude-এর মনোযোগের একটি অংশ ব্যবহার করে। 

অপ্রয়োজনীয় তথ্য যত বেশি থাকবে, Claude-এর কাছে আপনার আসল কাজের জন্য তত কম জায়গা ও মনোযোগ থাকবে।

## `CLAUDE.md` কোথায় রাখা যায়?

আপনি কয়েকটি স্থানে `CLAUDE.md` রাখতে পারেন:

* **প্রজেক্টের রুট (Project Root):** এটি সবচেয়ে প্রচলিত স্থান। ফাইলটি ভার্সন কন্ট্রোলে (যেমন Git) কমিট করলে পুরো টিম একই নির্দেশনা ও কনটেক্সট ব্যবহার করতে পারবে।

* **`.claude/CLAUDE.md`:** আপনি যদি কনফিগারেশন ফাইলগুলো আলাদা সাবডিরেক্টরিতে রাখতে পছন্দ করেন, তাহলে এটি একটি ভালো বিকল্প।

* **`~/.claude/CLAUDE.md`:** এটি ব্যবহারকারী-স্তরের (user-level) ডিফল্ট ফাইল। এখানে যা লিখবেন, তা আপনার সব প্রজেক্টেই প্রযোজ্য হবে।

## ব্যক্তিগত পছন্দের জন্য `CLAUDE.local.md`

যদি এমন কিছু ব্যক্তিগত পছন্দ বা সেটিংস থাকে, যা ভার্সন কন্ট্রোলে রাখতে চান না—যেমন:

এই ফাইলটি **`.gitignore`**-এ যোগ করে রাখুন, যাতে এটি Git-এর মাধ্যমে ভার্সন কন্ট্রোলে না যায়।

## ফাইলের নাম অবশ্যই সঠিক হতে হবে

ফাইলের নাম **case-sensitive**।

অর্থাৎ, নামটি অবশ্যই **`CLAUDE.md`** হতে হবে—

* `CLAUDE` অংশটি **সব বড় হাতের (UPPERCASE)** অক্ষরে,
* আর `.md` অংশটি **ছোট হাতের (lowercase)** অক্ষরে।

Claude Code মেমোরি ফাইল লোড করার সময় ঠিক এই নামটিই খোঁজে।

# কীভাবে আপনার `CLAUDE.md` ফাইল সাজাবেন

এটাই সবচেয়ে গুরুত্বপূর্ণ অংশ। প্রশ্ন হলো—**`CLAUDE.md`-এ আসলে কী কী থাকা উচিত?**

## যে বিষয়গুলো অবশ্যই থাকা উচিত

### ১. প্রজেক্টের পরিচিতি (Project Context)

প্রথমেই সংক্ষেপে লিখুন, **এই প্রজেক্টটি কী নিয়ে**।

একটি মাত্র বাক্যই Claude-কে পুরো প্রজেক্ট সম্পর্কে ধারণা দিতে পারে।

উদাহরণ:

> "এটি একটি Next.js-ভিত্তিক ই-কমার্স অ্যাপ, যেখানে Stripe পেমেন্ট ইন্টিগ্রেশন রয়েছে।"

এমন একটি বাক্য Claude-কে আপনার ধারণার চেয়েও বেশি তথ্য দেয় এবং কাজের প্রেক্ষাপট বুঝতে সাহায্য করে।

আপনার কোড লেখার নিয়ম ও পছন্দগুলো পরিষ্কারভাবে লিখুন।

যেমন:

* ES Modules ব্যবহার করবেন, নাকি CommonJS?
* Named Export ব্যবহার করবেন, নাকি Default Export?
* TypeScript-এর কোনো নির্দিষ্ট নিয়ম আছে কি?

যতটা সম্ভব নির্দিষ্টভাবে লিখুন।

উদাহরণ হিসেবে,

❌ "কোড সুন্দরভাবে ফরম্যাট করো।"

এটি খুবই অস্পষ্ট।

বরং লিখুন,

✅ "Named Export ব্যবহার করো, Default Export নয়।"

### ৩. কমান্ড (Commands)

Claude যেন জানে কোন কাজের জন্য কোন কমান্ড চালাতে হবে।

যেমন—

* টেস্ট চালানো

আপনি যখন Claude-কে এসব কাজ করতে বলবেন, তখন সে এখানকার কমান্ডগুলোই ব্যবহার করবে।

### ৪. গুরুত্বপূর্ণ সতর্কতা (Gotchas)

যেমন—

* কোনো API Endpoint নির্দিষ্ট Header Format ছাড়া কাজ করে না।
* এমন কোনো ফাইল আছে, যেটি কখনো সরাসরি পরিবর্তন করা উচিত নয়।

# একটি সম্পূর্ণ উদাহরণ

ধরুন, এটি একটি Next.js প্রজেক্টের `CLAUDE.md`:

```md
# Project: ShopFront

Next.js 14 ভিত্তিক একটি ই-কমার্স অ্যাপ্লিকেশন, যেখানে App Router, Stripe Payments এবং Prisma ORM ব্যবহার করা হয়েছে।

## Code Style

- TypeScript-এর Strict Mode ব্যবহার করতে হবে।
- `any` টাইপ ব্যবহার করা যাবে না।
- Default Export নয়, Named Export ব্যবহার করতে হবে।
- CSS-এর জন্য শুধুমাত্র Tailwind Utility Classes ব্যবহার করতে হবে।
- আলাদা Custom CSS ফাইল তৈরি করা যাবে না।

## Commands

- `npm run dev` : ডেভেলপমেন্ট সার্ভার চালু করবে (পোর্ট 3000)
- `npm run test` : Jest টেস্ট চালাবে।
- `npm run test:e2e` : Playwright End-to-End টেস্ট চালাবে।
- `npm run lint` : ESLint পরীক্ষা চালাবে।
- `npm run db:migrate` : Prisma Migration চালাবে।

## Architecture

- `/app` : Next.js App Router-এর Pages এবং Layout
- `/components/ui` : পুনঃব্যবহারযোগ্য (Reusable) UI Components
- `/lib` : Utility Functions এবং Shared Logic
- `/prisma` : Database Schema এবং Migration Files
- `/app/api` : API Routes

## Important Notes

- `.env` ফাইল কখনো Git-এ Commit করা যাবে না।
- `/app/api/webhooks/stripe`-এ থাকা Stripe Webhook Handler অবশ্যই Signature Validation করবে।
- Product Image লোকাল সার্ভারে নয়, Cloudinary-তে সংরক্ষিত থাকে।
- Authentication Flow সম্পর্কে বিস্তারিত জানতে `@docs/authentication.md` দেখুন।
```

## কেন এই কাঠামো কার্যকর?

Claude এই ধরনের `CLAUDE.md` খুব সহজে এবং দক্ষতার সঙ্গে পড়তে পারে, কারণ—

* বিষয়গুলো স্পষ্ট **Heading** দিয়ে ভাগ করা হয়েছে।
* তথ্যগুলো **Bullet Point** আকারে সাজানো, তাই দ্রুত স্ক্যান করা যায়।
* অস্পষ্ট নির্দেশনার বদলে **নির্দিষ্ট কমান্ড** দেওয়া হয়েছে।

ফলে Claude দ্রুত প্রজেক্টের নিয়ম বুঝে সেই অনুযায়ী কাজ করতে পারে।

`CLAUDE.md` কত বড় হওয়া উচিত? **৩০০ লাইনের মধ্যে** রাখা। যত ছোট হবে, তত ভালো।
তবে আমি এমন অনেক প্রজেক্টও দেখেছি, যেখানে একটু বড় `CLAUDE.md` রাখা যৌক্তিক।
আর কোনো তথ্য যদি শুধুমাত্র নির্দিষ্ট পরিস্থিতিতে প্রয়োজন হয়, তাহলে আমি সেটি আলাদা একটি ফাইলে রাখি এবং `CLAUDE.md` থেকে সেটির রেফারেন্স দিই।

**`@path/to/file`** সিনট্যাক্স ব্যবহার করা হয়:

* `CLAUDE.md`-এ শুধুমাত্র সবচেয়ে গুরুত্বপূর্ণ এবং প্রয়োজনীয় নির্দেশনাগুলো রাখা।
* আর নির্দিষ্ট বিষয়ের বিস্তারিত নির্দেশনাগুলো আলাদা Markdown ফাইলে রাখা।
* এরপর `@imports` ব্যবহার করে সেগুলোর রেফারেন্স দেওয়া।

* আর `/packages/ui`-তে কাজ করলে, UI Component-এর জন্য নির্ধারিত নিয়মগুলোই অনুসরণ করবে।

# `CLAUDE.md` কত বড় হওয়া উচিত?

সাধারণ পরামর্শ হলো **৩০০ লাইনের মধ্যে** রাখা। যত ছোট হবে, তত ভালো।

কারণ **Context Tokens** খুবই মূল্যবান। `CLAUDE.md` যত বড় হবে, Claude-কে তত বেশি তথ্য পড়তে হবে, ফলে আসল কাজের জন্য উপলব্ধ কনটেক্সট কমে যেতে পারে।

তবে আমি এমন অনেক প্রজেক্টও দেখেছি, যেখানে একটু বড় `CLAUDE.md` রাখা যৌক্তিক।

যদি আপনার কোডবেসে—

* জটিল নিয়ম (Complex Conventions) থাকে,
* অস্বাভাবিক ডিজাইন প্যাটার্ন (Unusual Patterns) ব্যবহার করা হয়,
* অথবা বিশেষ কিছু বিষয় আগে থেকেই জানা জরুরি হয়,

তাহলে শুরুতেই সেই তথ্যগুলো Claude-কে জানিয়ে দেওয়া ভালো। এতে Claude ভুল ধারণা করে কাজ শুরু করবে না, পরে বারবার সংশোধনও করতে হবে না।

আমার অভিজ্ঞতায়, আমি শুধু সেই তথ্যগুলোই `CLAUDE.md`-এ রাখি, **যেগুলো Claude-এর কাজ শুরু করার আগেই জানা দরকার।**

আর কোনো তথ্য যদি শুধুমাত্র নির্দিষ্ট পরিস্থিতিতে প্রয়োজন হয়, তাহলে আমি সেটি আলাদা একটি ফাইলে রাখি এবং `CLAUDE.md` থেকে সেটির রেফারেন্স দিই।

# `@imports` সিস্টেম

`CLAUDE.md`-এ অন্য ফাইল অন্তর্ভুক্ত (import) করার সুবিধা রয়েছে।

এটি করার জন্য নিচের মতো **`@path/to/file`** সিনট্যাক্স ব্যবহার করা হয়:

```text
See @README.md for project overview
See @docs/api-patterns.md for API conventions
See @package.json for available npm scripts
```

---

## কেন এটি উপকারী?

এই সুবিধার কারণে আপনি আপনার মূল `CLAUDE.md`-কে ছোট ও পরিষ্কার রাখতে পারেন।

বিস্তারিত নির্দেশনাগুলো আলাদা Markdown ফাইলে লিখে রাখুন, তারপর `@imports` দিয়ে সেগুলোর রেফারেন্স দিন।

যখন প্রয়োজন হবে, Claude সেই ফাইলের বিষয়বস্তুও পড়ে নেবে।

---

# কোন কোন ফাইল ইমপোর্ট করা যায়?

আপনি বিভিন্ন ধরনের পথ (Path) ব্যবহার করতে পারেন।

### Relative Path

```text
@docs/style-guide.md
```

এটি বর্তমান প্রজেক্টের `docs` ফোল্ডারের `style-guide.md` ফাইলকে নির্দেশ করে।

---

### Absolute Path

সম্পূর্ণ (Absolute) Path দিয়েও ফাইল ইমপোর্ট করা যায়।

---

### User-Level File

এমনকি আপনার ব্যক্তিগত Claude কনফিগারেশন থেকেও ফাইল ব্যবহার করা যায়।

উদাহরণ:

```text
@~/.claude/my-preferences.md
```

# Recursive Import

`@imports` **Recursive**-ও হতে পারে।

অর্থাৎ,

* `CLAUDE.md` একটি ফাইল ইমপোর্ট করল,
* সেই ফাইল আবার আরেকটি ফাইল ইমপোর্ট করতে পারে,
* এবং সেই ফাইলও আরও অন্য ফাইল ইমপোর্ট করতে পারে।

তবে এই সুবিধাটি **সতর্কতার সঙ্গে ব্যবহার করা উচিত**।

অতিরিক্ত Recursive Import ব্যবহার করলে ফাইলগুলোর মধ্যে জটিল রেফারেন্সের একটি "গোলকধাঁধা" (maze) তৈরি হতে পারে, যা বোঝা এবং রক্ষণাবেক্ষণ করা কঠিন হয়ে যায়।

# আমার ব্যবহৃত পদ্ধতি

শেষ পর্যন্ত আমি যে পদ্ধতিটি সবচেয়ে কার্যকর বলে পেয়েছি, তা হলো—

* `CLAUDE.md`-এ শুধুমাত্র সবচেয়ে গুরুত্বপূর্ণ এবং প্রয়োজনীয় নির্দেশনাগুলো রাখা।
* আর নির্দিষ্ট বিষয়ের বিস্তারিত নির্দেশনাগুলো আলাদা Markdown ফাইলে রাখা।
* এরপর `@imports` ব্যবহার করে সেগুলোর রেফারেন্স দেওয়া।

এর ফলে মূল `CLAUDE.md` সংক্ষিপ্ত, পরিষ্কার এবং সহজে পড়ার মতো থাকে, আবার প্রয়োজন হলে Claude বিস্তারিত তথ্যও সহজেই খুঁজে পায়।

# `.claude/rules/` দিয়ে মডিউলার নিয়ম (Modular Rules)

বড় প্রজেক্টের জন্য আরেকটি ভালো পদ্ধতি হলো **`.claude/rules/`** ডিরেক্টরি ব্যবহার করা।

একটি বড় `CLAUDE.md` ফাইলে সব নির্দেশনা একসঙ্গে রাখার পরিবর্তে, আপনি নিয়মগুলোকে আলাদা আলাদা Markdown ফাইলে ভাগ করে রাখতে পারেন।

উদাহরণ:

```text
your-project/
├── .claude/
│   ├── CLAUDE.md           # প্রজেক্টের প্রধান নির্দেশনা
│   └── rules/
│       ├── code-style.md   # কোড লেখার নিয়ম
│       ├── testing.md      # টেস্টিং সংক্রান্ত নিয়ম
│       └── security.md     # নিরাপত্তা সংক্রান্ত নির্দেশনা
```

এখানে—

* `CLAUDE.md`-এ থাকবে প্রজেক্টের মূল নির্দেশনাগুলো।
* `code-style.md`-এ থাকবে কোড স্টাইলের নিয়ম।
* `testing.md`-এ থাকবে টেস্টিং সংক্রান্ত নির্দেশনা।
* `security.md`-এ থাকবে নিরাপত্তা (Security) সংক্রান্ত নিয়ম।

---

## এটি কীভাবে কাজ করে?

`.claude/rules/` ফোল্ডারের **সব Markdown (`.md`) ফাইল** Claude স্বয়ংক্রিয়ভাবে পড়ে।

এগুলো **মূল `CLAUDE.md`-এর সমান অগ্রাধিকার (Priority)** পায়।

এখানে আলাদা করে `@import` ব্যবহার করার প্রয়োজন নেই।

শুধু `.claude/rules/`-এ ফাইলগুলো রেখে দিলেই Claude সেগুলো স্বয়ংক্রিয়ভাবে অন্তর্ভুক্ত (Load) করবে।

## কেন এটি উপকারী?

বড় টিমে সাধারণত বিভিন্ন সদস্য বিভিন্ন অংশের দায়িত্বে থাকেন।

যেমন—

* Frontend টিম `code-style.md` রক্ষণাবেক্ষণ করবে।
* Security টিম `security.md` আপডেট করবে।
* QA টিম `testing.md` দেখাশোনা করতে পারে।

এতে সবাইকে একটি বিশাল `CLAUDE.md` ফাইল একসঙ্গে সম্পাদনা করতে হয় না।

ফলে **Merge Conflict** হওয়ার সম্ভাবনাও অনেক কমে যায়।

## এটি কীভাবে কাজ করে?

অর্থাৎ, **যে অংশে কাজ করবে, শুধু সেই অংশের অতিরিক্ত নির্দেশনাই পড়বে।**
