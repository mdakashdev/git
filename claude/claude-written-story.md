- After working on the `Project` section, I work on the `Important Notes` section because working on it often brings up many additional details and can even lead to the creation of more sections.

---

1. Project / Package

- `package overview` - A one-sentence description of the entire package/project that provides a clear overall understanding of its purpose and scope.
- `package goal` - To state the purpose clearly and specifically
- `architecture` - To explain shortly what each folder in the codebase is, why it exists, and what is being done inside it.
- `Commands` -  Briefly explain the basic commands from the `package.json` file and the purpose for which each command is used.
- `important notes` - Based on the package overview and goals, we will define some common and specific rules here—what can and cannot be done, and what should be done. The main purpose is to keep everything within context and prevent unnecessary work.
- `Styling` - Since styling is a common concern, I’ll think about the styling approach and document what the styling should be here.

4. Important Notes

```text
When writing the `Important Notes` section, it becomes easier to define notes and rules by thinking in terms of different segments or parts.

For example: **Common, UI Kit, Bricks, Package**. These are the parts I identified in my project, but you may find more parts depending on your project.

Then, think specifically about each part—for example, **Common**—and decide what notes or rules should be added so that Claude can provide better output and stay within the project context.

The interesting part is that while writing the `Important Notes`, many additional things may come up that require detailed instructions. If you feel that a particular part is becoming too large because it needs too many instructions, separate that part from `Important Notes` and create a dedicated section for it.

```

> Nothing is fixed here. This file should always evolve and change as needed, and over time, it will become the **heart of this project**, containing everything essential to it.


---

Project section নিয়ে কাজ করার পর আমি `Important Notes` section নিয়ে কাজ করি, কারণ এই section নিয়ে কাজ করার সময় অনেক অতিরিক্ত বিষয় সামনে আসে এবং সেখান থেকে আরও নতুন section তৈরি হতে পারে।


- পুরো package/project সম্পর্কে এক বাক্যে এমন একটি বর্ণনা, যা এর উদ্দেশ্য ও পরিধি সম্পর্কে স্পষ্ট ধারণা দেয়।
- উদ্দেশ্যটা **point-by-point** বা **সংক্ষেপে নির্দিষ্ট করে বলা**।
- Codebase-এর প্রতিটি folder কী, কেন এটি আছে এবং এর ভেতরে কী কাজ করা হচ্ছে—তা সংক্ষেপে ব্যাখ্যা করা।
- `package.json` ফাইলের basic command-গুলো কোন উদ্দেশ্যে ব্যবহার করা হয়, তা সংক্ষেপে উল্লেখ করা।
- Package overview এবং goals-এর ভিত্তিতে এখানে কিছু **common এবং specific rules** সেট করা হবে—কী করা যাবে, কী করা যাবে না এবং কী করা উচিত। এর মূল উদ্দেশ্য হলো সবসময় **context-এর মধ্যে থাকা** এবং **অপ্রয়োজনীয় কোনো কাজ করা থেকে বিরত থাকা**।
- যেহেতু styling একটি common বিষয়, তাই styling approach কী হবে, সেটা নিয়ে চিন্তা করে এখানে লিখব।



```text
`Important Notes` section লেখার সময় বিভিন্ন **segment বা part** অনুযায়ী চিন্তা করলে notes বা rules তৈরি করা সহজ হয়।
যেমন: **Common, UI Kit, Bricks, Package**। এগুলো আমার project-এ পাওয়া কিছু part, তবে তোমার project অনুযায়ী আরও অনেক part পাওয়া যেতে পারে।
এরপর প্রতিটি part নিয়ে আলাদাভাবে চিন্তা করতে হবে। যেমন, **Common** নিয়ে ভাবতে হবে—কী কী note বা rule দিলে Claude আমার জন্য ভালো output দেবে এবং আমার project-এর context-এর বাইরে চলে যাবে না।
মজার বিষয় হলো, `Important Notes` লেখার সময় অনেক নতুন বিষয় সামনে আসতে পারে, যেগুলোর জন্য বিস্তারিত instruction দেওয়ার প্রয়োজন হতে পারে। তখন যদি কোনো একটি part-এর instruction দিতে গিয়ে দেখো যে point অনেক বেশি হয়ে যাচ্ছে, তাহলে সেই part-টাকে `Important Notes` থেকে আলাদা করে একটি **dedicated section** হিসেবে রাখা ভালো।
```

এখানে কিছুই স্থির নয়। প্রয়োজন অনুযায়ী এই file-টি সবসময় পরিবর্তিত ও উন্নত হতে থাকবে এবং সময়ের সঙ্গে সঙ্গে এটি এই project-এর **heart** হয়ে উঠবে, যেখানে project-এর জন্য প্রয়োজনীয় সবকিছু থাকবে।


**Nothing is fixed here.**

`CLAUDE.md`-কে আমি static documentation হিসেবে দেখছি না। Project যত evolve করবে, requirements যত পরিবর্তন হবে, আমাদের understanding যত গভীর হবে—এই file-টাও তত change করবে।

# Post

আজকে একটা project-এর `CLAUDE.md` file লিখতে বসেছিলাম।

আমার কাছে মনে হয়েছে, অন্তত এই file-টা AI-কে দিয়ে না লিখিয়ে সময় নিয়ে নিজে লেখা উচিত। 

ঠিকভাবে লিখতে পারলে, এটা ধীরে ধীরে পুরো project-এর **context hub** হয়ে উঠতে পারে।

তাই file-টা লেখার সময় পুরো বিষয়টাকে আমি ৪টা section-এ ভাগ করেছি:

**1. Project / Package**
**2. Reference**
**3. Status Tracking**
**4. Important Notes**

আজকে শুধু **Section 1: Project** নিয়ে বলি।

তার আগে একটু overall idea—

**Reference section** রাখার কারণ হলো, project-এ সময়ের সাথে অনেক documentation, guideline বা external reference প্রয়োজন হতে পারে। সবকিছু `CLAUDE.md`-এর মধ্যে রাখলে file অপ্রয়োজনীয়ভাবে বড় হয়ে যাবে। তাই reference গুলো আলাদা `docs` folder-এর মধ্যে রাখার চিন্তা করেছি।

**Status Tracking** section-এর উদ্দেশ্য হলো project-এর কাজের progress track করা—কোন কাজ complete, কোনটা ongoing, আর কোনটা এখনো শুরু হয়নি। এজন্য প্রয়োজন অনুযায়ী status file update করা হবে।

আর **Important Notes** section-এ থাকবে project-এর জন্য গুরুত্বপূর্ণ common এবং specific rules—যেগুলো কাজ করার সময় বারবার মনে রাখা দরকার।

এবার আসি **Project section**-এ।

এখানেই আমার কাছে সবচেয়ে interesting অংশটা ছিল।

আমি আগে থেকে কোনো fixed template নিয়ে বসিনি। বরং `CLAUDE.md` লিখতে লিখতেই নিজেকে একটা প্রশ্ন করেছি:

> **“কোন কোন information থাকলে Claude এই project-টাকে শুধু codebase হিসেবে না দেখে, একটা actual project হিসেবে বুঝতে পারবে?”**

এই চিন্তা থেকেই Project section-টাকে কয়েকটা ছোট অংশে ভাগ করেছি:

### 📦 Package Overview

পুরো package/project সম্পর্কে এক বাক্যে এমন একটা description, যেটা purpose এবং scope সম্পর্কে দ্রুত একটা clear ধারণা দেয়।

### 🎯 Package Goal

Project-এর মূল উদ্দেশ্য কী—সেটা clearly এবং specifically define করা।

### 🏗️ Architecture

Codebase-এর প্রতিটি folder কী, কেন আছে এবং সেখানে কী ধরনের কাজ হচ্ছে—সেটার একটা concise overview।

### ⚡ Commands

`package.json`-এ থাকা basic commands এবং প্রতিটি command কোন উদ্দেশ্যে ব্যবহার করা হয়—তার সংক্ষিপ্ত explanation।

### 🎨 Styling

Styling যেহেতু প্রায় সব component-এর ক্ষেত্রেই গুরুত্বপূর্ণ এবং consistency ধরে রাখা দরকার, তাই project-এ styling কীভাবে করা হবে এবং কোন approach follow করা হবে—সেটাও এখানে define করার পরিকল্পনা করছি।

তবে একটা বিষয় খুব important—

**Nothing is fixed here.**

`CLAUDE.md`-কে আমি static documentation হিসেবে দেখছি না। Project যত evolve করবে, requirements যত পরিবর্তন হবে, আমাদের understanding যত গভীর হবে—এই file-টাও তত change করবে।

আমার কাছে ideal `CLAUDE.md` এমন একটা file, যেটা সময়ের সাথে সাথে project-এর **“source of context”** হয়ে উঠবে।

আর শেষ পর্যন্ত হয়তো এই file-টাই হয়ে যাবে পুরো project-এর **heart**—যেখানে project সম্পর্কে essential context, rules, references, progress এবং decisions—সবকিছুর একটা organized picture থাকবে।

আজকের গল্প এখানেই।
সময় পেলে পরের পোস্টে **Reference section** নিয়ে লিখব।
